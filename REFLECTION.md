# REFLECTION.md — Engineering Reflections & Submission Review

### 1. What assumptions did you make?
I assumed that the legacy portal might use standard REST conventions (such as `/api/v1/meters` with standard limit/offset query parameters and HTTP 401 on failed logins) as suggested by typical take-home examples, but I verified before relying on them. Live reconnaissance proved that the portal is a SvelteKit application using form submissions to `/login`, requiring an `Origin` header for CSRF protection, returning HTTP 200 with a failure payload on bad credentials, and serializing meter attributes in SvelteKit devalue format alongside separate REST endpoints (`/portal/meters/search`, `/portal/meters/{id}/geo`, `/portal/meters/{id}/energy`). Furthermore, the search API only supported fixed 20-item pages (`page=1, 2, ...`), requiring our wrapper to assemble a multi-page buffer to serve exact arbitrary `limit` and `offset` slices across page boundaries. I also assumed that consumption registers represented cumulative energy readings rather than interval delta consumption because the kWh and kVAh values increased monotonically across 30-minute intervals.

### 2. Which part was the most difficult, and how did you get unstuck?
The most challenging part was reverse-engineering the SvelteKit application's data loading patterns without relying on full browser automation (which encountered a driver download issue). I became unstuck by downloading and analyzing the compiled client JavaScript bundles (`entry/app.03ZTmlg3.js` and node components `4.2Bgc2kUI.js`, `5.C4dYcCRt.js`, `6.l777LXKL.js`). This revealed the exact routing table, CSRF requirements, the SvelteKit devalue structure on `/meters/[id]/__data.json`, the presence of two distinct schema versions (`legacy` using parameter arrays and `v2` using `classData` JSON strings), the HMAC-SHA256 signature scheme on `/portal/export`, and the date filtering parameters supported upstream.

### 3. If you had another day, what would you improve?
If given another day, I would implement an in-memory or Redis-backed sliding-window cache for frequently accessed static metadata such as meter nameplates and Distribution Transformers to reduce latency and protect the legacy portal from redundant requests. I would also add calculated interval consumption metrics (deriving delta kWh between consecutive readings while accounting for meter rollover or reset anomalies), implement background synchronization using the discovered HMAC-signed `/portal/export` endpoint for bulk data ingestion, and add automated rate-limiting buckets per API key on incoming consumer requests.

### 4. What mistake did you make while solving this?
Early in the reconnaissance phase, I initially attempted to POST login credentials directly to `/` and without the `Origin` header, which triggered SvelteKit's CSRF rejection (`HTTP 403 Forbidden: Cross-site POST form submissions are forbidden`) followed by `HTTP 405 Method Not Allowed`. I also initially enabled `http2=True` in `httpx.AsyncClient` without installing the optional `h2` dependency, which caused an import error during the initial test run. I quickly identified the error from the traceback and removed the unnecessary HTTP/2 flag.

### 5. If you were reviewing your own submission, what would you criticise?
I would critique the hierarchy endpoint's pagination strategy and the synchronous multi-page search buffering. While `/portal/dts` contains 40 transformers across 2 pages and can be fetched quickly in 2 requests, on a grid with tens of thousands of transformers, sequentially paging through all DTs synchronously in the request handler would degrade response latency. Similarly, requesting deep offsets with large limits in `/meters` currently buffers up to 10 upstream 20-item pages synchronously. While we guarded against infinite loops with bounded page limits and break conditions on partial pages, a production deployment should pre-aggregate and index the grid hierarchy and meter indices asynchronously in a dedicated persistence layer.
